# Physical data ledger

Generated by `python3 tools/nagano_data.py map baseroms/us/baserom.z64 analysis/data_map`
(plus the unit verification logs).

`rom_map.tsv` is a half-open, gap-free, non-overlapping interval map of the
12,582,912-byte retail ROM. Every non-code byte has one category and stage, and
`tools/nagano_data.py reconstruct` regenerates every non-code interval from its
structured representation and compares it byte-for-byte with the ROM.

| Category | Bytes |
|---|---:|
| ROM header / IPL3 boot | 4,096 |
| Executable code (CPU text, RSP microcode, overlay text; owned by code matching) | 796,368 |
| Code-unit data (jump tables, overlay data) | 53,129 |
| Initialized data | 92,001 |
| Read-only data | 27,964 |
| Pointer / offset tables | 4,976 |
| Strings | 362 |
| s16x6 record streams (raw file-table entries) | 86,400 |
| libaudio banks and VADPCM samples | 3,149,970 |
| Konami-LZ containers (asset files and music sequences) | 8,035,702 |
| Proven zero padding | 331,944 |
| Unknown | 0 |

Physical byte-exactness and nested decoding are separate claims. The 547 LZ
containers re-encode exactly from their decoded payloads, but the records inside
the 14.76 MB of decoded asset payload (models, textures, animations) are not yet
structurally decoded; `asset_inventory.tsv` reports their F3DEX structural-walk
counts as candidates only.
